# 2026-11-27

## 🚇 출근 — OS / 프로세스·스레드, 동기화, 가상 메모리

OS는 처음이라 프로세스와 스레드부터 시작해서 동기화(경쟁 조건, 뮤텍스, 데드락)를 거쳐 가상 메모리까지 갔어요.

### Q1. 프로세스와 스레드의 차이는? 메모리 구조(Code/Data/Heap/Stack) 관점에서 무엇을 공유하고 무엇을 따로 가지나요?
- **내 답**: 프로세스는 한 프로그램 기준이 돌아가는 단위, 스레드는 메모리에 올라갔을 때 돌아가는 단위. 프로세스 안에 여러 스레드가 있나? 기억이 안 남
- **채점**: 🔺
- **보충**:
  - 프로세스 = 디스크의 프로그램이 메모리에 올라가 OS로부터 자원을 할당받은 상태 (자원 할당의 단위)
  - 스레드 = 프로세스 안에서 CPU를 받아 실행되는 흐름의 단위. 프로세스는 최소 1개(메인 스레드)부터 여러 개까지 가짐
  - 공유: Code, Data, Heap / 스레드마다 따로: Stack, 레지스터(PC 포함)
  - 꼬리 질문 "CPU를 스레드별로 배정하나?": 맞음. 현대 OS는 스레드 단위로 스케줄링하고, 멀티코어면 스레드가 동시에 여러 코어를 씀
  - 개념 정리: [concepts/os/process-thread.md](../../../concepts/os/process-thread.md)

### Q2. 스레드 간 컨텍스트 스위칭이 프로세스 간보다 가벼운 이유는?
- **내 답**: 공유 영역이 있으니까 개인적으로 바뀌는 스택과 레지스터는 비교적 가벼워서?
- **채점**: 🔺
- **보충**:
  - 방향(공유 영역 덕분)은 맞음. 스택·레지스터 저장/복원은 프로세스 전환 때도 똑같이 일어나서 그 부분이 차이는 아님
  - 차이는 주소 공간. 프로세스 전환은 페이지 테이블 교체 → **TLB 무효화** + CPU 캐시 미스 증가. 스레드 전환은 같은 주소 공간이라 이 비용이 없음
  - TLB = 가상 주소→물리 주소 변환 결과를 CPU 안에 캐싱하는 하드웨어

### Q3. 크롬은 탭마다 프로세스, 톰캣은 요청마다 스레드를 쓰는 이유는? (멀티프로세스 vs 멀티스레드 장단점)
- **내 답**: 크롬은 자원 공유를 안 해도 되고, 톰캣은 해야 하나 보지
- **채점**: 🔺
- **보충**:
  - 멀티프로세스: 격리(하나 죽어도 나머지 무사, 보안 샌드박스) / 메모리·전환 비용 큼, IPC 필요
  - 멀티스레드: 가볍고 공유 쉬움 / 동기화 문제, 한 스레드 크래시가 프로세스 전체에 영향
  - 톰캣은 빈·캐시·커넥션 풀을 요청끼리 공유해야 하고 요청마다 프로세스를 띄우면 너무 무거움. "동기화는 직접 신경 써야 한다"까지 말하면 완성

### Q4. 두 스레드가 공유 변수 `count++`를 1000번씩 실행했는데 2000이 안 나올 수 있는 이유와 해결법은?
- **내 답**: 읽고 쓰는 게 다르니까 (1000→1001→1002 / 1000→1001 흐름을 그려 줌)
- **채점**: 🔺 (원인은 맞고 해결법이 빠짐)
- **보충**:
  - `count++`는 읽기→더하기→쓰기 세 단계라 원자적이지 않음. 두 스레드가 같은 값을 읽고 각자 쓰면 lost update (경쟁 조건), 공유 자원을 건드리는 구간 = 임계 영역
  - 해결: 락(뮤텍스, `synchronized`, `ReentrantLock`), 원자 연산(`AtomicInteger`, CAS), 공유 피하기(스레드 로컬, 불변 객체)

### Q5. 뮤텍스와 세마포어는 뭐가 다른가요?
- **내 답**: 몰라
- **채점**: ❌
- **보충**:
  - 뮤텍스: 한 번에 1개 스레드만, **소유권** 있음(잡은 스레드만 해제). 상호 배제 용도
  - 세마포어: 정수 카운터로 N개까지 동시 접근, 소유권 없음(다른 스레드가 signal 가능). 동시 접근 수 제한(커넥션 풀), 스레드 간 신호 전달(생산자-소비자)에 사용
  - 꼬리 질문 "소유권이 뭐야?": 동시에 몇 명이 쓰느냐가 아니라 **누가 락을 풀 수 있느냐**의 문제. 바이너리 세마포어와 뮤텍스는 겉보기엔 같지만 소유권 유무가 다름

### Q6. 데드락이 뭔가요? 발생 조건 4가지는?
- **내 답**: 서로 필요한 걸 서로 갖고 있어서 락이 안 풀림. 네 가지는 모르겠음
- **채점**: 🔺 (정의만 맞음, 4조건 모름)
- **보충**:
  - 4조건: 상호 배제, 점유 대기, 비선점, 순환 대기. 네 개가 모두 충족될 때 발생하고 하나만 깨도 예방됨
  - 실무: 락 획득 순서 고정(순환 대기 제거), `tryLock(timeout)`(점유 대기·비선점 제거)

### Q7. 계좌 이체에서 스레드 1은 A→B, 스레드 2는 B→A, 둘 다 `from` 락을 먼저 잡고 `to` 락을 잡는다. 어떤 일이 생기고 어떻게 막나요?
- **내 답**: 순서를 지정해 주고(가장 중요), 트라이락으로 시간 설정
- **채점**: 🔺 (해결은 맞고, 문제 상황 설명이 빠짐)
- **보충**:
  - 상황: 스레드 1은 A를 잡고 B 대기, 스레드 2는 B를 잡고 A 대기 → 순환 대기로 데드락
  - 해결: 이체 방향과 상관없이 **계좌 ID가 작은 쪽 락을 먼저** 잡음. 둘 다 A를 먼저 잡으니 한쪽이 A에서 대기할 뿐 B를 쥐고 기다리는 상황이 안 생김
  - 꼬리 질문 "이체 때 두 계좌를 다 잡나?": 맞음. 출금·입금 두 계좌를 모두 수정하므로 둘 다 락. 순서만 통일하는 것
  - DB 비관적 락에서도 같은 문제가 생기고, DB는 데드락을 감지해 한쪽 트랜잭션을 롤백함
  - 개념 정리: [concepts/os/sync-deadlock.md](../../../concepts/os/sync-deadlock.md)

### Q8. 가상 메모리는 왜 필요한가요? 물리 메모리보다 큰 프로그램을 실행할 수 있는 이유는?
- **내 답**: 모르겠음
- **채점**: ❌
- **보충**:
  - 프로세스마다 0번지부터 시작하는 독립된 가상 주소 공간을 주고, MMU(+페이지 테이블, TLB)가 가상→물리 주소로 변환
  - 필요한 페이지만 물리 메모리에 올리고 나머지는 디스크(swap)에 둠(demand paging). 없는 페이지에 접근하면 page fault → OS가 디스크에서 로드
  - 꼬리 질문 "격리와 보호는 애초에 못 건드리는 거 아닌가?": 못 건드리는 이유가 가상 메모리 덕분. 없다면 물리 주소를 직접 써서 남의 메모리·커널 영역까지 읽고 쓸 수 있음. 있으면 페이지 테이블에 자기 페이지만 등록돼 있어서 남의 메모리로 가는 길이 없고, 매핑 없는 주소 접근은 segmentation fault
  - 개념 정리: [concepts/os/virtual-memory.md](../../../concepts/os/virtual-memory.md)

### Q1. [DB 복습] 인덱스가 있는데 풀스캔이 일어나는 경우와, 옵티마이저가 그렇게 고르는 이유는?
- **내 답**: 풀스캔이 더 빠르니까. 인덱스 찾고 또 데이터 가서 읽는 것보다 풀스캔이 낫겠다 싶으니까. 함수를 쓰거나, 복합 인덱스를 순서 반대로 찾거나, %가 앞에 있는 경우
- **채점**: ✅ (오답노트 졸업)
- **보충**:
  - 인덱스 → 테이블 이동은 행마다 랜덤 I/O, 풀스캔은 순차 I/O. 조건에 맞는 행 비율(선택도)이 높으면(대략 10~20% 이상) 풀스캔이 유리
  - 빠진 것: 형변환(문자 컬럼을 숫자로 비교하면 컬럼 쪽이 변환돼 인덱스를 못 탐)
  - 꼬리 질문 "랜덤 I/O는 어디서 랜덤이 붙나?": 인덱스 리프는 키 순서로 연결돼 있어 인덱스 안에서는 순차에 가까움. 하지만 매칭된 행은 테이블 페이지 여기저기에 흩어져 있어서 인덱스에서 테이블로 넘어가는 단계가 랜덤. InnoDB 세컨더리 인덱스는 PK로 클러스터드 인덱스를 한 번 더 탐색
  - 개념 정리: [concepts/db/index-not-used.md](../../../concepts/db/index-not-used.md)

### Q2. [Spring 복습] REQUIRED와 REQUIRES_NEW의 차이는? REQUIRES_NEW의 커넥션 풀 위험은?
- **내 답**: REQUIRES_NEW는 바깥 트랜잭션과 상관없이 새 트랜잭션을 만들어 동작. REQUIRED는 기존 트랜잭션이 있으면 끼고 없으면 새로 만듦. (풀 위험은 답 없음)
- **채점**: 🔺
- **보충**:
  - REQUIRES_NEW는 바깥을 보류(suspend)하고 새 커넥션을 따로 사용. 커밋·롤백이 독립
  - 풀 위험: 바깥이 커넥션 1개를 쥔 채 안쪽이 1개를 더 요청. 동시 요청 수가 풀 크기와 같으면 전부 안쪽 커넥션을 기다려 풀 고갈 데드락
  - 꼬리 질문 "REQUIRES_NEW에서 에러 나면 바깥도 롤백?": 안쪽만 롤백. 예외가 바깥 메서드까지 전파되면 바깥도 롤백되고, 바깥에서 catch하면 정상 커밋. REQUIRED와 달리 rollback-only 표시는 안 남음. 안쪽이 먼저 커밋된 뒤 바깥이 롤백되면 안쪽 결과는 남음
  - 꼬리 질문 "보류가 뭔가?": 바깥의 커넥션은 반납하지 않고 열어 둔 채, 스레드 바인딩만 떼어 보관했다가 안쪽이 끝나면 다시 이어 붙임
  - 개념 정리: [concepts/spring/transactional.md](../../../concepts/spring/transactional.md)

### Q3. [Spring 복습] `readOnly = true`의 효과는? (JPA / DB·인프라)
- **내 답**: 읽을 때 더티체킹을 안 함. 더티체킹은 스냅샷 비교인데 그걸 안 해서 성능이 좋음. 정리가 안 됨
- **채점**: 🔺 (JPA 쪽만 답함)
- **보충**:
  - JPA: 스냅샷을 안 만들어 변경 감지 생략, flush 모드 MANUAL
  - DB: 커넥션 `setReadOnly(true)` 힌트로 읽기 최적화
  - 인프라: 읽기/쓰기 분리 구조에서 레플리카 DataSource로 라우팅(`AbstractRoutingDataSource`)
  - 꼬리 질문 "트랜잭션 매니저한테 커넥션을 넘기나?": 넘기는 게 아니라 매니저가 DataSource에서 커넥션을 받아 `autoCommit=false`로 만들고 스레드 로컬에 바인딩. 같은 스레드의 JPA·JDBC가 그 커넥션을 같이 씀
  - 암기: flush 끄고, DB 힌트 주고, 레플리카로 보낸다

### Q4. [Java 복습] 서버가 가끔 몇 초씩 멈출 때 GC가 원인인지 어떻게 확인하고 대응하나요? STW는?
- **내 답**: gc dump를 봄. STW는 GC가 정리할 때 멈추는 것. 다른 알고리즘을 써서 여러 번 나눠서 GC가 도는 걸 쓸 듯
- **채점**: 🔺 (STW ✅, 확인 방법 혼동, 대응 방향은 맞음)
- **보충**:
  - 확인: GC 로그(`-Xlog:gc*`)와 `jstat -gcutil`로 pause 시간·Full GC 빈도·GC 후 Old 사용량을 봄. 힙 덤프(`jmap`, MAT)는 청소해도 Old가 안 줄어서 누수가 의심될 때 여는 것
  - 대응: G1(region으로 나눠 조금씩 정리), ZGC(대부분 앱과 동시에 처리) 같은 저지연 GC, 힙 크기 조정, 객체 생성 줄이기, 누수 수정
  - 개념 정리: [concepts/java/jvm-gc.md](../../../concepts/java/jvm-gc.md)

### Q5. [OS 재도전] A→B, B→A 이체가 동시에 일어날 때 데드락 상황과 해결은?
- **내 답**: 순서를 정해줘서 해결. 순환. 가진 걸 안 내려놓고 딴 걸 가지려 할 때. (나머지 두 조건은 기억 안 남)
- **채점**: 🔺 (해결은 맞음, 상황 설명과 순서 기준 빠짐)
- **보충**:
  - 상황: 스레드 1은 A를 쥐고 B 대기, 스레드 2는 B를 쥐고 A 대기
  - 해결: 방향과 무관하게 계좌 ID가 작은 쪽 락을 먼저 잡음. `tryLock(timeout)`은 보조
  - 4조건 암기 "상점비순": 상호 배제·점유 대기·비선점·순환 대기. 이번에 순환 대기·점유 대기만 떠올림
  - 개념 정리: [concepts/os/sync-deadlock.md](../../../concepts/os/sync-deadlock.md)
