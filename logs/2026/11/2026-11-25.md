# 2026-11-25

## 🚇 출근 — Spring / 트랜잭션

Spring은 처음이라 문제 사이사이에 프록시, 커넥션, ThreadLocal 개념 설명을 많이 섞었어요.

### Q1. `@Transactional`을 붙이면 스프링 내부에서 트랜잭션이 어떻게 시작되고 커밋/롤백될까요?
- **내 답**: All or Nothing. 한곳에 모았다가 문제 있으면 롤백, 아니면 커밋
- **채점**: 🔺
- **보충**:
  - 원자성 개념은 맞지만 "스프링이 어떻게 해주는지"(동작 원리)가 빠짐
  - 앱 시작 때 `@Transactional` 빈마다 AOP 프록시 1개 생성 → 호출을 `TransactionInterceptor`가 가로챔
  - 트랜잭션 매니저가 커넥션 풀에서 커넥션을 받아 `autoCommit = false`, ThreadLocal에 보관 → 같은 스레드의 Repository들이 같은 커넥션 사용
  - 쿼리는 모아두지 않고 즉시 DB로 감. DB가 미확정 상태로 들고 있다가 commit/rollback (JPA의 쓰기 지연은 별개 기능)
  - 개념 정리: [concepts/spring/transactional.md](../../../concepts/spring/transactional.md)

### Q2. 같은 클래스에서 트랜잭션 없는 A가 `this.B()`로 `@Transactional` B를 부르면?
- **내 답**: 적용 안 될 것 같다. 같은 클래스 내에서는 전파되는데 A에 트랜잭션이 없어서
- **채점**: 🔺
- **보충**:
  - 결론은 맞고 이유가 다름. 전파와는 무관하고 **프록시를 거치지 않아서**
  - 원본 A 안의 `this`는 프록시가 아니라 원본 자신 → B의 인터셉터가 동작 안 함
  - A에 트랜잭션이 없으면 B는 auto-commit으로 쿼리마다 커밋 → 예외 나도 롤백 안 되고 조용히 데이터가 깨짐
  - A에 트랜잭션이 있으면 B는 A에 얹혀 실행되지만, B에 붙인 REQUIRES_NEW·readOnly·rollbackFor는 무시됨
  - 해결: 별도 빈으로 분리(권장), A에 붙이기, self-injection. private 메서드도 같은 이유로 안 먹음

### Q3. `@Transactional` 메서드에서 Checked 예외(IOException)가 터지면 롤백? 커밋?
- **내 답**: 커밋. 예외에 따라 커밋되는 게 있고 안 되는 게 있다
- **채점**: 🔺
- **보충**:
  - RuntimeException·Error → 롤백, Checked → 커밋
  - 설계 이유: Checked는 예상 가능·복구 가능한 비즈니스 예외로 봄(호출자가 처리하고 작업은 살림), Unchecked는 예상 못 한 버그·시스템 오류라 데이터 상태를 못 믿으니 롤백. EJB 관례
  - `rollbackFor = Exception.class`로 변경 가능

### Q4. 전파 속성 REQUIRED vs REQUIRES_NEW, REQUIRES_NEW는 언제 쓸까?
- **내 답**: REQUIRES_NEW는 무조건 커밋돼야 하는 작업(로그 등). REQUIRED는 모름
- **채점**: 🔺
- **보충**:
  - 전파 속성 = 이미 트랜잭션이 있을 때 트랜잭션 메서드가 또 호출되면 어떻게 할지 정하는 규칙. 기본값이 REQUIRED라 자동으로 전파되는 것처럼 보임
  - REQUIRED: 있으면 참여, 없으면 생성 (한 커넥션, 하나 롤백되면 전부 롤백)
  - REQUIRES_NEW: 기존 트랜잭션 보류 → 새 커넥션으로 독립 트랜잭션
  - 주의: 안쪽 예외를 바깥에서 안 잡으면 바깥도 롤백 / 요청 하나가 커넥션 2개 → 커넥션 풀 데드락 위험
  - 전파 속성도 프록시를 거쳐야 적용됨

### Q5. REQUIRED로 참여한 다른 빈의 메서드에서 RuntimeException → 바깥에서 catch하고 정상 종료하면 커밋될까?
- **내 답**: 안 될 것 같은데 모르겠다
- **채점**: ❌
- **보충**:
  - 전부 롤백 + `UnexpectedRollbackException`
  - 참여자는 커밋/롤백 권한이 없어서 공유 중인 물리 트랜잭션에 **rollback-only** 표시만 함 (스프링 트랜잭션 상태 객체, DB가 아님)
  - catch해도 표시는 안 지워짐 → 주인이 커밋 시도할 때 표시 보고 롤백
  - 원칙: 모든 논리 트랜잭션이 커밋돼야 물리 트랜잭션이 커밋됨
  - 해결: 안쪽을 REQUIRES_NEW로 / 안쪽에서 예외를 직접 잡기 / noRollbackFor

### Q6. `@Transactional(readOnly = true)`의 효과와 조회 메서드에 붙이는 이유는?
- **내 답**: 수정·변경은 안 되나?
- **채점**: 🔺
- **보충**:
  - JPA: flush 모드가 MANUAL → 스냅샷을 안 만들고 변경 감지·flush를 생략 → 메모리·CPU 절약
  - JDBC: `Connection.setReadOnly(true)` → DB가 읽기 전용 최적화 (MySQL은 트랜잭션 ID 할당 생략 등)
  - 레플리카 라우팅: readOnly 여부로 읽기 전용 DB로 보내는 구성에 활용
  - "수정 안 되나?": JPA 엔티티 변경은 flush가 안 돼서 **에러 없이 조용히 반영 안 됨**, 직접 UPDATE/INSERT는 MySQL·PostgreSQL에서 에러
  - 조회 전용이라는 의도를 코드로 드러내는 효과도 있음
  - 꼬리 질문 "스냅샷을 원래 찍어?": readOnly가 아니면 조회할 때마다 찍음. JPA는 `update()`가 없어서, 조회 시 처음 상태를 복사(스냅샷)해 두고 flush 때 현재 엔티티와 필드 단위로 비교해 UPDATE를 만듦(변경 감지). 메모리 약 2배 + 비교 CPU 비용 → readOnly면 스냅샷·flush를 생략해서 이 비용을 안 냄

## 🏠 퇴근 — 복습 (오답노트)

### Q1. (오답노트) DB 인덱스는 왜 B+Tree로 구현할까?
- **내 답**: B+Tree는 리프에 데이터가 있어서 구간 검색에 용이
- **채점**: 🔺
- **보충**:
  - 구간 검색이 빠른 진짜 이유는 **리프끼리 연결 리스트**로 이어져 있어서 (리프에 데이터가 있다는 것만으론 부족)
  - 중간 노드에 키만 → fan-out↑ 높이↓ 디스크 I/O↓, 항상 리프까지 내려가 탐색 비용 일정
  - 꼬리 질문 "리프에 위에서 거친 키가 다 있어야 하냐?": 맞음. 리프에 모든 키가 있고, 중간 노드 키는 그 복사본(이정표). B-Tree는 각 키가 트리에 한 번만 있음
  - 구조 차이 3가지 정리: ① 데이터 위치 ② 리프에 중간 키 복사본 ③ 리프 연결 리스트. 면접에선 ①·③에 "그래서 왜 좋냐"를 붙이기
  - 개념 보강: [concepts/db/b-plus-tree.md](../../../concepts/db/b-plus-tree.md)

### Q2. (오답노트) 인덱스가 있는데 풀 테이블 스캔이 일어나는 경우는?
- **내 답**: 쿼리 쪽은 `LIKE '%검색어'`, 옵티마이저 쪽은 값이 너무 흔하면 굳이 인덱스를 안 탐
- **채점**: 🔺
- **보충**:
  - 두 방향 구분은 정확. 쿼리 쪽 예시가 하나뿐 → 컬럼 가공, 묵시적 형변환, 복합 인덱스 선두 컬럼 누락
  - 옵티마이저 쪽은 이유가 빠짐 → 인덱스 경유는 행마다 테이블로 가는 **랜덤 I/O**, 풀스캔은 **순차 I/O**. 비율이 대략 20~25% 넘으면 풀스캔이 쌈
  - 꼬리 질문 "가공은 왜 안 돼?": 인덱스엔 원본 값만 정렬돼 있어서, 가공 값으로는 시작 위치를 못 찾고 모든 행을 가공해 비교해야 함. 형변환도 DB가 컬럼에 함수를 씌우는 것
  - 복합 인덱스는 이유가 살짝 다름: b는 같은 a 안에서만 정렬돼 있어서 전체로는 흩어짐
  - 꼬리 질문 "인덱스→데이터 이동이 I/O?": 맞음. 페이지(16KB) 단위로 인덱스 페이지 → 테이블 페이지를 읽음. 행마다 반복하면 랜덤 I/O. 버퍼 풀에 있으면 디스크 안 읽음
  - 개념 보강: [concepts/db/index-not-used.md](../../../concepts/db/index-not-used.md)

### Q3. (오답노트) 트랜잭션 없는 A가 `this.B()`로 `@Transactional` B를 부르면?
- **내 답**: 적용 안 됨. 프록시 없이 바로 불려서 바로 커밋이 들어감
- **채점**: ✅ (출근 때 틀린 "전파 때문" → "프록시를 안 거쳐서"로 교정, 졸업)
- **보충**:
  - `this`는 원본 객체라 프록시가 끼어들 틈이 없음 → auto-commit으로 쿼리마다 커밋, 예외 나도 롤백 안 됨
  - 해결: 별도 빈 분리(권장), A에 `@Transactional`, self-injection
  - 꼬리 질문 "트랜잭션이 없으면 프록시가 없냐?": 클래스에 `@Transactional` 메서드가 하나라도 있으면 빈이 프록시로 감싸짐. 이 예시에선 프록시는 있지만 A 호출은 그냥 원본으로 넘김
  - 꼬리 질문 "A에 붙여서 B가 얹히는 게 전파?": 엄밀히는 아님. B의 어노테이션은 읽히지도 않고, 같은 스레드의 ThreadLocal 커넥션을 쓰니 A 트랜잭션 안에 있을 뿐. 그래서 B의 REQUIRES_NEW도 무시됨
  - 꼬리 질문 "트랜잭션과 프록시는 한 세트?": 선언적 트랜잭션에선 맞음. `TransactionTemplate`(프로그래밍 방식)은 프록시 없이 동작

### Q4. (오답노트) REQUIRED 안쪽 예외를 바깥에서 catch하면 커밋?
- **내 답**: 안 됨. 체크가 돼서 에러가 터짐 (에러 이름은 기억 안 남)
- **채점**: 🔺
- **보충**:
  - 안쪽은 트랜잭션 주인이 아니라 롤백 권한이 없어서 **rollback-only 표시**만 함
  - 바깥 커밋 시 표시를 보고 롤백 + **`UnexpectedRollbackException`**
  - 해결: 안쪽을 REQUIRES_NEW로 분리하거나 안쪽에서 예외 직접 처리

### Q5. (오답노트) REQUIRED vs REQUIRES_NEW, 트래픽이 몰리면?
- **내 답**: REQUIRED는 열려 있는 트랜잭션의 커넥션을 공유, NEW는 새 트랜잭션. NEW는 커넥션을 두 개씩 써서 문제
- **채점**: 🔺
- **보충**:
  - REQUIRED는 "없으면 새로 생성"도 포함
  - REQUIRES_NEW는 기존 트랜잭션을 **보류(suspend)** 후 독립 커밋·롤백 → 감사 로그 등
  - 문제 이름은 **커넥션 풀 데드락**: 바깥이 풀을 다 잡은 상태에서 안쪽이 커넥션을 기다리고, 바깥은 안쪽이 끝나야 반납 → 서로 대기, 타임아웃까지 멈춤
  - 대응: 풀 크기 산정, 바깥 트랜잭션 종료 후 처리(이벤트 등)로 구조 변경
