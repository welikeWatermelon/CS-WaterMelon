# 2026-11-26

## 🚇 출근 — Java / JVM·GC, equals·hashCode, String

Java는 처음이라 JVM 구조, GC, HashMap 저장 과정까지 설명을 많이 섞었어요.

### Q1. `.java` 소스가 실행되기까지 JVM은 어떤 과정을 거치나요? (클래스 로더, Runtime Data Area, 실행 엔진)
- **내 답**: 모르겠음. JVM은 머신이라는 것만 알고 머신이 뭔지도 모름
- **채점**: ❌
- **보충**:
  - JVM = 프로그램을 대신 실행해 주는 가상의 컴퓨터. OS 위에서 돌아서 "한 번 작성하면 어디서든 실행"이 가능
  - javac로 `.class`(바이트코드) 생성 → 클래스 로더가 메모리에 적재 → Runtime Data Area(Heap, Stack, Method Area) → 실행 엔진(인터프리터 + JIT, GC)
  - 개념 정리: [concepts/java/jvm-gc.md](../../../concepts/java/jvm-gc.md)

### Q2. `int a = 10; Person p = new Person();` 에서 a, p, Person 객체는 어디에 저장되나요?
- **내 답**: a는 스택, p는 힙
- **채점**: 🔺
- **보충**:
  - a(기본형 지역변수)는 Stack ✅
  - p는 참조 변수라 **Stack**, `new Person()`으로 만든 **객체는 Heap**. 스택의 p가 힙 객체를 가리킴
  - 메서드가 끝나면 스택의 p가 사라지고, 아무도 가리키지 않는 힙 객체가 GC 대상

### Q3. GC는 안 쓰는 객체를 어떻게 판단하나요? 힙을 Young/Old로 나누는 이유는?
- **내 답**: 시간 기준이 있나? (모르겠음)
- **채점**: ❌
- **보충**:
  - 판단 기준은 시간이 아니라 **도달 가능성(reachability)**. GC Root(Stack 지역변수, static 변수, 실행 중 스레드)에서 참조를 따라 닿을 수 없으면 쓰레기
  - static 변수도 GC Root라 가리키는 객체는 계속 살아 있음 → static 컬렉션에 쌓기만 하면 메모리 누수
  - 약한 세대 가설: 대부분 객체는 금방 죽음 → Young에서 자주 빠르게(Minor GC), 오래 산 객체는 Old로 승격해 드물게(Major GC)
  - 객체 헤더의 age가 Minor GC에서 살아남을 때마다 증가, 임계값(HotSpot 기본 최대 15) 넘으면 Old로 승격

### Q4. Stop-The-World가 뭔지, 왜 문제가 되나요?
- **내 답**: 처음 들음
- **채점**: ❌
- **보충**:
  - GC가 돌 때 애플리케이션 스레드를 전부 멈추는 것. 정리 중 참조가 바뀌면 판단이 꼬이기 때문
  - 멈춘 동안 요청 처리가 안 돼서 응답 지연·타임아웃. Major GC에서 특히 길어짐
  - Serial/Parallel(STW 김) → G1(Region으로 쪼개 STW 짧게) → ZGC(대부분 동시 처리, STW 아주 짧게)

### Q5. 운영 서버가 가끔 몇 초씩 멈춘다. CPU·DB는 정상. GC가 원인이라면 뭘 확인하나요?
- **내 답**: GC 로그
- **채점**: 🔺
- **보충**:
  - 방향은 맞음. 로그에서 Pause 시간(=STW)이 응답 지연 시각과 겹치는지, Full GC 빈도, GC 후 Old 사용량이 안 줄면 누수 의심
  - `-Xlog:gc*:file=gc.log`, `jstat -gc <pid>`, Prometheus+Grafana, 누수 의심 시 힙 덤프를 MAT로 분석
  - 대응: 힙 크기 조정, GC 변경(G1/ZGC), 누수 코드 수정

### Q6. `==`와 `equals()`의 차이는? equals가 true면 hashCode도 같아야 하는 이유는?
- **내 답**: 주소 비교, 안의 값 비교. 안의 값을 해시로 바꾸면 같으니까
- **채점**: 🔺
- **보충**:
  - `==`는 참조 비교. `equals()`는 오버라이드해야 값 비교(기본 구현은 `==`와 같음)
  - 이유: HashMap이 hashCode로 버킷을 정하고 그 안에서 equals로 확인함. equals가 true인데 hashCode가 다르면 다른 버킷에 들어가 get이 null, Set에 중복
  - 역방향(hashCode 같다 → equals 같다)은 필수 아님(해시 충돌)
  - 같은 필드로 `equals`와 `hashCode`를 같이 오버라이드

### Q7. `"abc"` 리터럴 두 개와 `new String("abc")`에 `==`를 쓰면?
- **내 답**: true, false / 스트링풀
- **채점**: ✅
- **보충**:
  - 리터럴은 String Pool에서 공유 → s1 == s2 true, `new String`은 Heap에 새 객체 → false
  - 값 비교는 equals, `intern()`으로 Pool 객체를 받을 수 있음

### Q8. String은 왜 불변(immutable)으로 만들었나요?
- **내 답**: 같은 걸 만들면 꺼내서 쓸 수 있어서 자원을 아낌
- **채점**: 🔺
- **보충**:
  - Pool 공유로 메모리 절약은 맞음. 단 불변이라서 공유가 가능한 것(가변이면 한 곳의 변경이 다른 곳에 영향)
  - 추가 이유: HashMap 키로 안전(해시 불변, hashCode 캐싱), 스레드 안전, 보안(검증 후 값 변경 방지)

## 🏠 퇴근 — 복습 (오답노트, Spring 트랜잭션)

### Q1. (오답노트) `@Transactional`을 호출하면 내부에서 트랜잭션이 어떻게 시작되고 끝날까?
- **내 답**: 프록시로 호출 → 프록시가 트랜잭션 매니저에 시작 요청 → 매니저가 풀에서 커넥션을 꺼내 ThreadLocal에 줌 → 그 스레드는 같은 커넥션 사용 → 정상이면 커밋, 예외면 롤백
- **채점**: ✅ (처음엔 흐름만 말해서 🔺, 다시 정리하면서 졸업)
- **보충**:
  - 키워드: AOP 프록시 → 트랜잭션 매니저 → 커넥션 풀 → autoCommit=false → ThreadLocal → 같은 커넥션 → commit/rollback → 반납
  - "쿼리가 어디 담기나"는 ThreadLocal에 묶인 같은 커넥션. 한 커넥션 = 한 DB 트랜잭션이라 같이 롤백됨
  - 개념 정리: [concepts/spring/transactional.md](../../../concepts/spring/transactional.md) 맨 위 "키워드 정리"

### Q2. (오답노트) Checked 예외가 나면 롤백될까? 왜 그렇게 설계했을까?
- **내 답**: 롤백 안 되고 커밋. 일부러 Checked는 잡으려고 한 것
- **채점**: ✅
- **보충**:
  - Checked = 예상 가능한 비즈니스 예외라 호출자가 처리한다고 보고 커밋, Unchecked/Error = 예상 못 한 오류라 롤백
  - 롤백하려면 `rollbackFor = Exception.class`

### Q3. (오답노트) REQUIRED vs REQUIRES_NEW
- **내 답**: REQUIRES_NEW는 바깥이 롤백돼도 안쪽은 롤백 안 되게 새 커넥션을 주는 것. REQUIRED는 기본값인지 헷갈림
- **채점**: 🔺
- **보충**:
  - REQUIRED가 기본값 맞음. 전파 속성은 선택지 전체의 이름이고 REQUIRED는 그중 기본값 (이전에 헷갈린 지점)
  - REQUIRED: 있으면 참여(같은 커넥션), 없으면 생성 / REQUIRES_NEW: 기존 보류 + 새 커넥션
  - 빠진 부분: 바깥이 커넥션을 쥔 채로 안쪽이 하나 더 요구 → 요청 하나가 커넥션 2개 → 풀 고갈 시 **풀 데드락**

### Q4. (오답노트) REQUIRED 안쪽 예외를 바깥이 catch하면 커밋될까?
- **내 답**: 롤백온리가 true로 돼서 바깥에서 예외가 남
- **채점**: ✅ (졸업)
- **보충**:
  - 참여자는 rollback-only 표시만 하고, catch해도 표시는 안 지워져서 바깥 커밋 시점에 전체 롤백 + `UnexpectedRollbackException`
  - 예외 이름까지 말하면 더 좋음. 회피법은 안쪽을 REQUIRES_NEW로 분리

### Q5. (오답노트) `readOnly = true`의 효과
- **내 답**: 데이터를 수정 안 하나?
- **채점**: 🔺
- **보충**:
  - "수정을 막는다"가 아니라 **수정 관련 작업을 생략하는 최적화**: flush 생략(MANUAL), 변경 감지 생략, 스냅샷 미생성, DB 읽기 전용 힌트, 레플리카 라우팅
  - 수정해도 에러 없이 조용히 반영만 안 됨 → 수정 방지 장치로 믿으면 안 됨. 주목적은 성능 + 읽기 전용이라는 의도 표시
  - 꼬리 질문 "스냅샷은 언제 찍나?": 조회해서 영속성 컨텍스트에 올리는 순간 최초 상태를 복사. 수정은 메모리에서만 바뀌고, flush 때 현재 값과 스냅샷을 비교해 다르면 UPDATE 생성(변경 감지)
  - readOnly면 스냅샷을 안 만들고 flush도 안 해서 엔티티 N개면 복사본 N개와 비교 비용이 사라짐
