# 클러스터드 vs 논클러스터드(세컨더리) 인덱스

## 한 줄 요약

둘 다 B+Tree인데, **리프 노드에 무엇이 들어 있느냐**가 달라요.

- **클러스터드**: 리프에 **행 데이터 전체**가 들어 있어요.
- **논클러스터드(세컨더리)**: 리프에 **인덱스 컬럼 값 + PK 값**만 들어 있어요.

## 비유

- 클러스터드 = 사전. 단어를 찾으면 그 자리에 뜻이 있어요.
- 세컨더리 = 책 뒤쪽 색인. 페이지 번호만 나오고, 그 페이지로 한 번 더 넘어가야 내용이 있어요.

## InnoDB에서

- **PK 기준으로 테이블 자체가 B+Tree로 저장**돼요. 이게 클러스터드 인덱스이고, 테이블당 **1개**예요.
- PK가 없으면 `UNIQUE NOT NULL` 인덱스를 쓰고, 그것도 없으면 숨겨진 row id를 만들어서 써요.
- 그래서 "클러스터드 = PK 인덱스"로 외워도 대부분 통해요. 정확히는 "데이터가 저장되는 기준이 되는 인덱스"예요.

## 조회 과정

`SELECT * FROM user WHERE email = 'a@b.com'` (email에 세컨더리 인덱스가 있는 경우)

1. email 인덱스 B+Tree를 타고 내려가 리프에서 **PK 값**을 얻어요.
2. 그 PK로 **클러스터드 인덱스를 한 번 더** 탐색해서 행을 읽어요. (PK 재탐색, 북마크 룩업)

→ 세컨더리는 B+Tree를 **2번**, 클러스터드(PK 조회)는 **1번** 타요.

## 파생 포인트

- **PK는 짧을수록 좋아요.** 모든 세컨더리 인덱스 리프에 PK가 복사돼 들어가서, PK가 크면 인덱스 전체가 커져요.
- **PK가 랜덤(UUID 등)이면 불리해요.** 행이 PK 순서로 정렬 저장되니, 랜덤 값은 중간 삽입이 많아지고 페이지 분할이 자주 일어나요. AUTO_INCREMENT는 항상 끝에 붙어서 삽입에 유리해요.
- **커버링 인덱스가 빠른 이유**: 세컨더리 인덱스만으로 필요한 컬럼을 다 얻으면 2단계(PK 재탐색)를 건너뛰어요.

## 면접용 한 줄

"클러스터드 인덱스는 리프에 행 데이터가 직접 저장된 인덱스로 InnoDB에서는 PK가 그 역할을 하고, 세컨더리 인덱스는 리프에 PK 값만 있어서 조회할 때 세컨더리 인덱스로 PK를 찾은 뒤 클러스터드 인덱스를 한 번 더 탐색합니다."
