# B-Tree vs B+Tree — 인덱스가 B+Tree인 이유

## 한 줄 요약

B+Tree는 **실제 데이터를 리프 노드에만 두고, 리프끼리 연결 리스트로 이어둔** B-Tree예요. 그래서 범위 검색이 빠르고, 검색 시간이 항상 일정해요.

## 두 구조의 차이

| | B-Tree | B+Tree |
|---|---|---|
| 데이터(또는 행 주소) 위치 | 모든 노드 (중간 노드에도 있음) | **리프 노드에만** |
| 중간 노드 역할 | 키 + 데이터 | 키만 (길 안내용 표지판) |
| 리프끼리 연결 | 없음 | **연결 리스트로 이어짐** |
| 검색 깊이 | 중간에서 찾으면 일찍 끝남 → 들쭉날쭉 | 항상 리프까지 → 일정 |
| 범위 검색 | 트리를 위아래로 오가며 순회 | 시작 리프를 찾고 옆으로 쭉 읽음 |

## 인덱스에 B+Tree가 유리한 이유

1. **범위 검색이 빠르다**
   `BETWEEN`, `>`, `ORDER BY`는 시작 위치만 트리로 찾고, 그다음은 리프의 연결 리스트를 따라 옆으로 읽으면 끝나요. B-Tree는 중간 노드에도 데이터가 흩어져 있어서 위아래로 오가야 해요.
2. **트리 높이가 낮다 → 디스크 I/O가 적다**
   DB는 노드 하나를 페이지(InnoDB 기준 16KB) 하나로 읽어요. 중간 노드에 데이터 없이 키만 넣으면 한 페이지에 키가 더 많이 들어가요(fan-out 증가). 그러면 트리가 낮아지고, 루트에서 리프까지 읽는 페이지 수가 줄어요. 보통 높이 3~4로 수천만 건을 다뤄요.
3. **성능이 예측 가능하다**
   어떤 키든 항상 리프까지 내려가니까 검색 비용이 같아요.

## 함께 알아두면 좋은 것

- **"B-Tree 인덱스"라고 부르지만 실제 구현은 대부분 B+Tree**예요. MySQL InnoDB, PostgreSQL 모두 그래요.
- InnoDB 클러스터드 인덱스(PK)는 리프에 **행 전체**가, 세컨더리 인덱스는 리프에 **PK 값**이 들어 있어요. 그래서 세컨더리 인덱스로 찾으면 PK로 한 번 더 찾아가요.
- 해시 인덱스는 `=` 검색은 O(1)이지만 정렬이 없어서 범위 검색을 못 해요. B+Tree가 기본인 이유이기도 해요.

## 면접용 한 줄

"B+Tree는 데이터를 리프에만 두고 리프를 연결 리스트로 이어둬서, 범위 검색을 리프만 옆으로 읽어 처리할 수 있고, 중간 노드에 키만 담아 fan-out이 커지니 트리가 낮아져 디스크 I/O가 줄어듭니다. 그래서 DB 인덱스는 B+Tree를 씁니다."
