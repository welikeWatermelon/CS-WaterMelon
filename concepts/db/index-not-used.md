# 인덱스를 못 타는 경우

인덱스를 걸어도 풀 테이블 스캔이 나오는 이유는 두 갈래예요.

## 1. 쿼리 방식 때문에 못 타는 경우

B-Tree 인덱스는 컬럼 값이 정렬된 상태로 저장돼 있어서, 정렬 순서로 시작 위치를 찾을 수 있어야 인덱스를 쓸 수 있어요.

| 원인 | 예시 | 고치는 방법 |
|---|---|---|
| 앞쪽 와일드카드 | `LIKE '%검색어%'` | `LIKE '검색어%'`로 바꾸거나 전문 검색(GIN, FULLTEXT) 사용 |
| 컬럼 가공 | `WHERE YEAR(created_at) = 2026` | 범위 조건으로 변경 (`>= '2026-01-01' AND < '2027-01-01'`) |
| 묵시적 형변환 | varchar 컬럼에 `phone = 01012345678` | 비교 값 타입을 컬럼 타입에 맞추기 |
| 복합 인덱스 선두 컬럼 누락 | 인덱스 `(a, b)`에서 `WHERE b = ?` | 조건에 a 포함, 또는 컬럼 순서 조정 |

### 왜 못 타나? — 원인별 이유

- **컬럼 가공 / 형변환**: 인덱스에는 **원본 값**이 정렬돼 있어요. `YEAR(created_at)`이나 `CAST(phone)`처럼 바뀐 값은 인덱스에 없고, 그 값 기준으로 정렬돼 있다는 보장도 없어요. 그래서 시작 위치를 못 찾고, 모든 행을 하나씩 꺼내 **가공한 다음 비교**해야 해요 → 풀스캔. 형변환은 DB가 몰래 컬럼에 함수를 씌우는 것이라 가공과 같은 문제예요.
- **앞쪽 와일드카드**: 정렬은 앞글자부터라 `%검색어`는 시작점이 없어요.
- **복합 인덱스 선두 컬럼 누락**: 이유가 살짝 달라요. `(a, b)`는 a로 먼저 정렬하고 같은 a 안에서만 b가 정렬돼요. 전체로 보면 b는 **흩어져 있어서** b만으로는 시작 위치를 못 찾아요. (값을 가공해서가 아니라, b 기준 정렬이 없어서예요.)

> 한 줄로: **"인덱스의 정렬 순서를 이용해 시작 위치를 찾을 수 없으면 인덱스를 못 탄다."**

### 인덱스 → 테이블 이동이 왜 I/O?

DB는 데이터를 **페이지(InnoDB 16KB)** 단위로 디스크에 저장하고 읽어요.

1. 인덱스 B+Tree를 루트→리프로 내려가며 인덱스 페이지를 읽어요 (I/O 몇 번)
2. 리프에서 찾은 행 위치(InnoDB 세컨더리 인덱스면 PK)로 **실제 행이 있는 테이블 페이지**를 또 읽어요
3. 찾은 행이 많으면 2번을 행마다 반복 → 행들이 디스크 여기저기 흩어져 있으니 **랜덤 I/O**

풀스캔은 테이블 페이지를 앞에서부터 **연속으로** 읽어서(순차 I/O) 페이지당 비용이 훨씬 싸요.
참고로 페이지가 이미 메모리(버퍼 풀)에 있으면 디스크 I/O는 안 일어나요. 옵티마이저는 이것까지 대략 비용으로 계산해요.

## 2. 옵티마이저가 풀스캔을 고르는 경우

- 기준은 조건에 맞는 행의 비율(선택도)이에요.
- 인덱스를 타면 찾은 행마다 테이블로 다시 가서 읽어요(랜덤 I/O). 풀스캔은 앞에서부터 쭉 읽어요(순차 I/O).
- 읽을 비율이 높으면(흔히 20~25% 이상) 풀스캔이 더 싸서 옵티마이저가 풀스캔을 골라요.
- 카디널리티가 낮은 컬럼, 작은 테이블, 오래된 통계도 원인이에요. 통계는 `ANALYZE`로 갱신하고, 확인은 `EXPLAIN`으로 해요.

## 면접용 한 줄

"앞이 고정되지 않은 LIKE, 컬럼 가공, 형변환처럼 인덱스의 정렬 순서를 쓸 수 없는 쿼리는 인덱스를 못 타고, 결과 비율이 높으면 인덱스의 랜덤 I/O보다 풀스캔의 순차 I/O가 싸서 옵티마이저가 풀스캔을 고릅니다."
