# 동기화와 데드락

## 한 줄 요약

스레드가 공유 자원을 동시에 건드리면 **경쟁 조건**이 생기고, 이를 락으로 막다가 락을 서로 쥔 채 기다리면 **데드락**이 돼요.

## 경쟁 조건과 임계 영역

`count++`는 한 줄이지만 **읽기 → 더하기 → 쓰기** 세 단계라 원자적이지 않아요.

```
스레드 A: count 읽음(1000)
스레드 B: count 읽음(1000)
스레드 A: 1001 씀
스레드 B: 1001 씀   ← 두 번 더했는데 한 번만 반영 (lost update)
```

- **경쟁 조건(race condition)**: 실행 순서에 따라 결과가 달라지는 상황
- **임계 영역(critical section)**: 공유 자원을 건드리는 구간. 한 번에 한 스레드만 들어가게 해야 해요.

해결 방법은 세 가지예요.
- 락: 뮤텍스, Java의 `synchronized`, `ReentrantLock`
- 원자 연산: `AtomicInteger` (락 없이 CAS로 처리)
- 공유 피하기: 스레드 로컬, 불변 객체

## 뮤텍스 vs 세마포어

| | 뮤텍스 | 세마포어 |
|---|---|---|
| 동시 접근 | 1개 스레드만 | 값 N만큼 |
| 소유권 | **있음** (잡은 스레드만 해제) | **없음** (다른 스레드가 signal 가능) |
| 용도 | 상호 배제 | 동시 접근 수 제한(커넥션 풀), 스레드 간 신호 전달(생산자-소비자) |

- 소유권은 동시에 몇 명이 쓰느냐가 아니라 **누가 락을 풀 수 있느냐**의 문제예요.
- 값이 1인 바이너리 세마포어와 뮤텍스의 차이도 소유권이에요.
- 세마포어 연산: `wait(P)`로 값을 줄이고 `signal(V)`로 늘려요.

## 데드락 4조건

서로 필요한 자원을 쥔 채로 기다려서 영원히 멈추는 상태예요. 아래 네 개가 **모두 충족**될 때 발생해요.

1. **상호 배제**: 자원을 한 번에 한 스레드만 써요.
2. **점유 대기**: 자원을 쥔 채로 다른 자원을 기다려요.
3. **비선점**: 남이 쥔 자원을 강제로 뺏을 수 없어요.
4. **순환 대기**: A→B→A처럼 기다리는 고리가 생겨요.

하나만 깨도 예방돼요. 실무에서 흔한 두 가지는 이렇게예요.
- **락 획득 순서 고정**: 순환 대기를 제거해요.
- **`tryLock(timeout)`**: 일정 시간 못 잡으면 포기하고 쥔 락을 놓아요. 점유 대기와 비선점을 제거해요.

## 예시: 계좌 이체

A→B와 B→A가 동시에 일어나고 둘 다 `from` 락을 먼저 잡으면, 서로 상대가 쥔 락을 기다리다 데드락이 돼요. 이체는 출금·입금 두 계좌를 모두 수정하니까 둘 다 락을 잡아야 해요.

해결은 이체 방향과 상관없이 **계좌 ID가 작은 쪽을 먼저** 잡는 거예요.

```java
Account first  = from.getId() < to.getId() ? from : to;
Account second = from.getId() < to.getId() ? to : from;
synchronized (first) {
    synchronized (second) {
        // 이체 처리
    }
}
```

둘 다 같은 계좌를 먼저 잡으니 한쪽은 첫 락에서 대기할 뿐이고, 다른 락을 쥔 채 기다리는 상황이 생기지 않아요.

DB 비관적 락에서도 같은 문제가 생겨요. DB는 데드락을 감지해 한쪽 트랜잭션을 롤백하니까, 애플리케이션에서는 같은 순서로 락을 거는 게 기본이에요.
