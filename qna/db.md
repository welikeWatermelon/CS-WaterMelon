### 2026-11-24 — 인덱스를 못 타는 경우
**Q. 인덱스가 있는데도 풀 테이블 스캔이 일어나는 경우를 설명해 보세요.**
- 쿼리 방식 문제: 앞쪽 와일드카드 `LIKE '%x'`, 컬럼 가공(함수·연산), 묵시적 형변환, 복합 인덱스 선두 컬럼 누락 → 인덱스의 정렬 순서를 활용할 수 없음
- 옵티마이저 판단: 조회 결과 비율이 높으면 인덱스 경유 랜덤 I/O보다 풀스캔 순차 I/O가 더 싸서 풀스캔 선택. 낮은 카디널리티, 작은 테이블, 오래된 통계도 원인

### 2026-11-24 — B-Tree vs B+Tree
**Q. DB 인덱스는 왜 B-Tree가 아니라 B+Tree로 구현할까요?**
- B+Tree는 데이터를 리프에만 두고 리프를 연결 리스트로 이어둠 → 범위 검색 시 시작 리프만 찾고 옆으로 순차 읽기
- 중간 노드에 키만 있어 fan-out이 커짐 → 트리 높이가 낮아져 디스크 I/O 감소
- 항상 리프까지 내려가므로 검색 비용이 일정

### 2026-11-24 — 클러스터드 vs 논클러스터드 인덱스
**Q. 클러스터드와 세컨더리 인덱스는 어떻게 다르고, 세컨더리 인덱스로 조회하면 내부적으로 어떻게 동작하나요?**
- 클러스터드: 리프에 행 데이터 전체. InnoDB에서는 PK 기준으로 저장되며 테이블당 1개
- 세컨더리: 리프에 인덱스 컬럼 값 + PK 값. 조회하면 세컨더리 B+Tree에서 PK를 얻고, 클러스터드 인덱스를 한 번 더 탐색(총 2번)
- 파생: PK는 짧게(세컨더리에 복사됨), 랜덤 PK(UUID)는 페이지 분할 유발, 커버링 인덱스는 PK 재탐색을 생략

### 2026-11-25 — B+Tree 키 중복 / 인덱스와 I/O (복습 꼬리 질문)
**Q. B+Tree 리프에는 중간 노드의 키가 다 들어 있나요? 인덱스로 행을 찾는 게 왜 랜덤 I/O인가요?**
- B+Tree 리프에는 모든 키가 있고 중간 노드 키는 복사본(이정표). B-Tree는 각 키가 한 번만 존재
- 인덱스 페이지를 읽고 행 위치로 테이블 페이지를 또 읽음. 행이 흩어져 있어 행마다 랜덤 I/O → 비율이 높으면 순차 I/O인 풀스캔이 유리
- 컬럼 가공·형변환은 원본 값 정렬을 못 써서, 복합 인덱스 `(a,b)`의 b 단독은 b가 전체로 흩어져 있어서 못 탐. a 단독은 가능(leftmost prefix)

### 2026-11-27 — 인덱스인데 풀스캔 (복습)
**Q. 인덱스가 있는데 풀스캔이 일어나는 경우와 이유는?**
- 이유: 인덱스 → 테이블 이동은 행마다 랜덤 I/O, 풀스캔은 순차 I/O. 선택도가 낮아 조건에 맞는 행이 많으면(대략 10~20% 이상) 풀스캔이 유리
- 못 타는 경우: 컬럼 가공·함수, 형변환, 복합 인덱스 선두 컬럼 누락, `LIKE '%abc'`
- 랜덤이 붙는 지점: 인덱스 리프는 키 순서로 연결돼 순차에 가깝지만, 매칭된 행은 테이블 페이지에 흩어져 있어 인덱스에서 테이블로 넘어가는 단계가 랜덤
